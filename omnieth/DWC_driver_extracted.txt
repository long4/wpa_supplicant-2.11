Product Overview
1.1 General Product Description
The Synopsys IP MACsec includes a collection of software drivers. The software helps in quickly 
integrating the cores to the environment and provides a starting point for application development.
This software is environment-independent, although it can be run out of the box in a simulation together 
with the cores. The CoreConsultant® ITB testbench provides simulated interfaces for the C test 
environment, simulates traffic, and validates encryption/decryption. The C test environment and the ITB 
allow real case scenarios simulation of the core usage and use the drivers for control and configuration.
Figure 1-1 Relationship Between the C Test Environment and Testbench
1.2 File Structure
The MACsec drivers are included under /sim/c_libs. A Makefile available at this level is used to 
compile all the drivers and examples into a single c_lib.so library. The following folders are available at 
this level:
■ Drivers: This contains the drivers used to access the MACsec registers, error codes, and the register 
map.
■ Tests: These contain some top-level test functions, code for interfacing with the System Verilog 
sequences used for hardware and traffic simulation.

Drivers
2.1 Overview
The objective of this software driver implementation is to meet the requirement for many different 
applications in different environments. For example, different applications include automotive and 
consumer electronics whereas different environment include operating systems or bare-metal platforms. 
The simple design of this driver allows you to easily port the software implementation to the required 
spaces, simultaneously meeting the safety requirements expected of a Synopsys product.
2.2 Register Access Functions
The driver mostly includes simple register access functions used for reading and writing single registers 
defined in the register maps. In typical usage within the context of MACsec operation, some of these register 
access functions are used in logical succession, such as when installing a key.
2.2.1 Register Access Functions
Each register has one or two corresponding register access functions, according to its memory access 
attributes.

Examples
3.1 Overview
The DWC_macsec drivers include the following examples: 
■ Initialization Example: This example includes secure association initialization and the simulation of 
traffic to demonstrate the success of the initialization. 
■ FIPS Example: This example includes parsing and encryption or decryption of NIST vectors for FIPS 
140-3 validation.
■ IEEE Test Vectors Example: This example includes sending frames defined by the IEEE specification 
to verify the correct implementation of the IDE.
■ Safety Alarms Example: This example includes intentionally triggering errors in the DWC_macsec 
module and checking whether the correct safety alarm is triggered.
The following examples show how to use the drivers in real scenarios, both in mission and in test mode. 
They run out of the box in conjunction with the CoreConsultant® ITB testbench or are used as a starting 
point for application development.

Before using any API, it is necessary to initialize the DWC_macsec module using the dss_macsec_init() 
function and the UAES module using the dss_macsec_uaes_init() function.
If the configuration is created correctly, call the DWC_macsec_init() function to execute the initialization. 
This example consists of the following main steps:
1. Initial Setup
Set the test configurations using the dss_macsec_set_test_config() function. This function does the 
following: 
a. Read the device information using the dss_get_core_ver_num(), dss_get_core_ver_type(), and 
dss_get_macsec_ip_control() APIs.
b. Update the macsec_ip_control register using the dss_set_macsec_ip_control() API.
c. Set the minimum inter-fr ame gap writing to the macsec_cfg_min_ipg register using the 
dss_macsec_set_macsec_cfg_min_ipg() API.
d. Set the MACsec IP VLAN values by writing to the macsec_ip_vlan register using the 
dss_macsec_set_macsec_ip_vlan() API. 
e. Set the ether type filters to be used by writing to the ethertype_filter_x registers using the 
dss_macsec_set_ethertype_filter_x() API.
f. Set the ether type replace feature and its value by writing to the ethertype_replace register 
using the dss_macsec_set_ethertype_replace() API.
2. TX Secure Association Setup
a. Install the key for the secure association using the dss_macsec_uaes_install_key() API that does 
the following:
i. Write the key in the key_x registers in big-endian order using the 
dss_macsec_uaes_set_key() API.
ii. Write the key context to the ctrl.ctx_idx register field, the key size to the ctrl.key_sz 
register field, the encrypt enable to the ctrl.encrypt register field, and the mode to the 
ctrl.mode register field using the dss_macsec_uaes_set_ctrl() API. For more information on 
the key context, see the “Key Configuration and Key Swap” section in the Synopsys® Security 
IP MACsec Security Module Databook.
iii. Poll the stat.busy register field using the dss_macsec_uaes_get_stat() API until it is set to 
0x0.
iv. After the key is programmed, write 0x0 to the key_x registers using the 
dss_macsec_uaes_set_key() API to avoid key readback.
b. Program the secure association va lues into the SAD table using the 
dss_macsec_add_TX_SAD_entry() API, which does the following:
i. If the Extended Packet Number feature (XPN) is  not enabled, write the packet number in the 
tx_sad_0_low.pn_or_ssci register field using the dss_macsec_set_tx_sad_0_low() 
API. If XPN is enabled, write the Short Secure Channel Identifier (SSCI) to the 
tx_sad_0_low.pn_or_ssci register field.

3. TX SALT Table Setu p (if XPN is enabled)
a. Program the salt values for each  SA in the SALT table using the 
dss_macsec_add_TX_SALT_entry() API, which does the following: 
i. Write the lowest 32 bits of the 96-bit salt value into the tx_salt_table_0 register using the 
dss_macsec_set_tx_salt_table_0() API.
ii. Write the middle 32 bits of the 96-bit salt value in the tx_salt_table_1 register using the 
dss_macsec_set_tx_salt_table_1() API.
iii. Write the higher 32 bits of  the 96-bit salt value in the tx_salt_table_2 register using the 
dss_macsec_set_tx_salt_table_2() API.
iv. Write 0x1 to the tx_salt_prg.type register field to indicate that this is a write operation 
to the SALT table and the secure association index of the table to write to the 
tx_salt_prg.entry register field using the dss_macsec_tx_salt_prg() API.
v. Poll the tx_salt_pg.busy register field using the dss_macsec_uaes_get_tx_salt_pg() API 
until it is set to 0x0.
b. Repeat step a until all the salt values are programmed into the TX SALT table.

3.3 FIPS Example
The FIPS example validates that the DWC_macsec is FIPS 140-3 certified, according to the NIST Special 
Publication 800-38B. For more information on the Computer Security Resource Center, see 
https://csrc.nist.gov/publications/sp800.
The NIST file contains hundreds of vectors for different keys, IVs, plaintexts, Additional Authentication 
Data (AAD), and MAC lengths. 
The vectors are parsed using the functions in the nist_parse file and stored in a structure called 
test_vector that contains all the information about a given vector. This process helps to use the NIST 
vectors in the example and execute the test.
The FIPS example consists of the following steps:
1. Initialize the UAES module using the dss_macsec_uaes_init() API.
2. Inhibit the AES output by writing 0x1 to the misc_config.inhibit_output register field using 
the dss_macsec_uaes_set_misc_config() API.
3. Enable test mo de by writing 0x1 to the fips_self_test_ctl.fips_self_test_ena register 
field. (Optional) Enable the internal self-checker by setting the 
fips_self_test_ctl.fips_self_test_check register field. Write to the sel_test_ctl 
register using the dss_macsec_uaes_set_fips_self_test_ctl() API.
4. Load the key corresponding to the NIST vector th at is tested in mission mode using the specific 
context for test mode. For CTR mode tests, the key must be loaded with the ctrl.mode register field 
set to 1.
5. For GCM and CTR modes, write the IV correspond ing to the NIST vector being assessed to the 
fips_self_test_iv registers using the dss_macsec_uaes_set_fips_self_test_iv() API.
6. Create a buffer with the AAD and the Message (MSG ) present in the test vector, and if the self-
checker is enabled in step 3, create another one with the expected AAD and MSG. These buffers are

composed of data blocks with a width that is calculated using the get_aes_msg_width() function. 
AAD and MSG cannot share the same 128-bit block. Hence, if the data block contains AAD and 
plaintext, the AAD needs to be padded with zeros to the nearest 128-bit value (if it does not already 
terminate on a 128-bit boundary). 
For example, for a test vector with a 160-bit AAD and a 408-bit MSG, with a supported message 
width of 256 bits for the AES core, the data is sent to the AES over three different blocks as follows:
a. First block: The 160-bit AAD is padded with 96 ze ros on the right. Since the AAD is bigger than 
128 bits, the message starts in the next block.
b. Second block: The first 256 bits of the message. 
c. Third block: The last 152 bits of the messa ge are padded with 104 zeros on the right. 
7. Load the AAD or MSG using the macsec_set_in_msg() function. This function loads the contents of 
the current block in 32-bit chunks into the fips_self_test_idata registers using the

8. Load the fips_self_test_att register:
a. Write 0x1 to the fips_self_test_att.self_test_aad register field if the current data

macsec_set_out_msg() function. This function loads the contents of the current block (with the 
expected vector) in 32-bit chunks into the fips_self_test_odata registers using the 
dss_macsec_uaes_set_fips_self_test_odata() API. 
For GCM mode, write into the fips_self_test_mac registers using the 
dss_macsec_uaes_set_fips_self_test_mac() API to load the expected MAC vector.
10. For non-GCM modes, write the size of the AAD contained in the block to the 
fips_self_test_aad_size.aad_size register field using the 
dss_macsec_uaes_set_fips_self_test_aad_size() API.
11. For non-GCM modes, write the size of the MSG contained in the block to the 
fips_self_test_msg_size.msg_size register field using the 
dss_macsec_uaes_set_fips_self_test_msg_size() API.

a multi-round packet (eop == 1 && sop == 0).

3.6 Running Examples
You can execute the Init, FIPS, IEEE test vector, and safety alarms examples out of the box by selecting the 
tests in the Software Examples group in the Setup and Run Simulations section of CoreConsultant®. The 
software libraries and design are both compiled and linked, and the selected tests are executed. 
For compiling the example code, a C compiler with C11 support is required. GCC 9.2.0 is used in the 
internal testing.
